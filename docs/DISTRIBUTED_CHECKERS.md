# Распределённая проверка прокси

ProxyHarbor может проверять очередь прокси на любом количестве внешних Linux VPS. Основной сервер остаётся control plane и единственным владельцем PostgreSQL. Агенты устанавливают только исходящие HTTPS-соединения к нему, поэтому открывать на checker-хостах новые входящие порты не требуется.

## Подключение узла

1. Укажите `CheckerAgentDeployment__PublicBaseUrl` — корневой HTTPS origin основного сервиса.
2. Откройте в панели **Узлы проверки**, нажмите **Подключить VPS** и задайте имя, IP, SSH-порт, root-пользователя, одноразовый пароль, concurrency и размер партии.
3. Control plane устанавливает SSH-соединение, проверяет host key и автоматически выбирает режим:
   - если Docker уже установлен, атомарно запускает именованный контейнер `proxyharbor-checker-agent`;
   - без Docker скачивает release-архив и отдельный приватный .NET runtime, проверяет SHA-256/SHA-512 и запускает hardened systemd-службу.
4. Дождитесь первого heartbeat и состояния **На связи**.

Установщик не ставит Docker, не вызывает пакетный менеджер, не публикует порты и не изменяет чужие контейнеры или службы. На одном VPS поддерживается одна управляемая установка агента.

SSH-пароль существует только в памяти текущего административного запроса: он не сохраняется в БД, backup, ответах API или конфигурации агента. Агент получает случайный токен; в PostgreSQL хранится только SHA-256 hash, а plaintext — на checker-хосте в файле с режимом `0400`. При повторном развёртывании токен меняется только после успешного запуска новой версии.

Первое подключение использует trust on first use. Сохранённый SHA-256 fingerprint блокирует соединение с хостом, SSH-ключ которого неожиданно заменён. После легитимной переустановки VPS удалите прежнюю запись с подтверждённого хоста и создайте её заново.

## Как распределяется работа

- агент отправляет heartbeat и атомарно запрашивает партию;
- PostgreSQL выбирает только просроченные задания через `FOR UPDATE SKIP LOCKED`;
- партия получает UUID lease с ограниченным сроком;
- агент продлевает lease во время проверки и загрузки результатов;
- control plane принимает результат только от владельца действующей lease и только с полным точным набором элементов;
- запись результатов и завершение audit run выполняются согласованно;
- локальный валидатор основного сервера продолжает забирать свободную очередь как резервный исполнитель.

Две ноды не получают один и тот же прокси одновременно. Поздний результат старой lease не может перезаписать более свежую проверку.

## Отказы и восстановление

Если агент, VPS или сеть исчезли, lease автоматически истекает, незавершённый validation run помечается ошибкой, а вся партия возвращается в общую очередь. Другой агент или локальный валидатор заберёт её без ручного вмешательства. Остановка одного узла не останавливает сбор, API и остальные проверки.

При краткой недоступности control plane агент повторяет heartbeat и отправку с ограниченным экспоненциальным backoff. После истечения lease устаревший результат отклоняется, а партия безопасно проверяется заново. При недоступности PostgreSQL новые lease не выдаются и частичные результаты не подтверждаются.

## Настройка производительности

- **Concurrency** — число параллельных сетевых проб. Начните со 100–200 и повышайте после проверки CPU, RAM, NAT/conntrack и лимита файловых дескрипторов.
- **Размер партии** — количество прокси в одной аренде. Практический старт: примерно `2 × concurrency`.
- Размещайте узлы в разных сетях и странах, чтобы уменьшить влияние локальной маршрутизации и блокировок.
- Для небольшого VPS учитывайте примерно 100–200 МБ постоянного диска; установщик дополнительно требует настраиваемый запас свободного места для атомарного обновления.

## Эксплуатация

Панель показывает heartbeat, текущую lease, версию агента, удалённый IP, ошибки и накопительные счётчики. Узел можно приостановить без удаления. Повторное развёртывание требует SSH-пароль, сверяет fingerprint, сначала проверяет новую установку и только затем меняет рабочую версию и токен.

Удаление сначала останавливает и удаляет только именованный контейнер либо `proxyharbor-checker-agent.service`, каталог приложения/runtime и token-файлы, затем удаляет центральную запись. При недоступном VPS запись сохраняется, чтобы не создавать ложное ощущение удаления удалённого секрета.

В backup schema v7 входят настройки и аудит узлов, но не SSH-пароли и agent-токены. После disaster recovery повторно разверните каждый узел.

## Требования к checker-VPS

- Linux x64 или arm64 с systemd;
- root SSH-доступ для управляемой установки в `/opt/proxyharbor-checker`;
- `curl`, `tar`, `sha256sum`, `sha512sum`, `useradd` и `systemctl`;
- не менее `NativeMinimumFreeMegabytes` свободного места в файловой системе `/opt` (по умолчанию 300 МБ);
- исходящий HTTPS к control plane, GitHub Releases и официальному Microsoft CDN runtime;
- Docker необязателен; если он уже установлен и работает, используется опубликованный multi-arch образ.

Нативный archive является framework-dependent и одинаков для x64/arm64. Архитектурный .NET runtime закреплён точной версией и встроенным SHA-512. Release archive проверяется опубликованным рядом `.sha256`; ошибка любой проверки останавливает установку до замены рабочей версии.
