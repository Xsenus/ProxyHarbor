# Каталог источников ProxyHarbor

Пользовательские источники [My-Proxy](https://www.my-proxy.com/free-proxy-list.html) поддерживают HTML-страницы `free-proxy-list.html`, `free-proxy-list-2.html` … `free-proxy-list-10.html`, `free-elite-proxy.html`, `free-anonymous-proxy.html`, `free-transparent-proxy.html`, `free-socks-4-proxy.html` и `free-socks-5-proxy.html` на `https://www.my-proxy.com`. Извлекается только единственный опубликованный блок списка; HTTP/SOCKS-протокол задаётся категорией страницы. Неизвестная разметка, login/error body, дополнительные контейнеры и непубличные адреса не становятся кандидатами. Успешный источник обновляется раз в час; conditional validators, HTTPS/SSRF-проверки, лимит body и сохранённая очередь импорта остаются действующими. Эти страницы не добавлены автоматически во встроенный каталог; адрес из списка требует отдельной проверки перед статусом Alive.

JSON-тип `HTTP/HTTPS` распознаётся как `Http`: [Sunny9577](https://github.com/sunny9577/proxy-scraper/blob/master/spec.js) группирует его с HTTP и публикует `IP:PORT` в HTTP-выгрузке. Этот явный тип не наследует TLS-режим источника и не подтверждает поддержку CONNECT; validator проверяет подключение отдельно.

Для HTTP CONNECT поверх TLS до самого proxy endpoint используйте `HttpTls` с системной проверкой сертификата прокси либо явно выбранный `HttpTlsUnverified` для шифрования без проверки личности прокси. Проверка сертификата сайта назначения остаётся обязательной в обоих режимах. Прежняя категория `Https` сохраняет смысл HTTP CONNECT без TLS до прокси. В источнике с выбранным TLS-режимом строки `IP:PORT` и `https://IP:PORT` сохраняют этот режим; смешанный текст может явно указывать `http+tls://` и `http+tls-unverified://`, а JSON — `HttpTls` и `HttpTlsUnverified`. Старые источники не переинтерпретируются. [Databay](https://github.com/databay-labs/free-proxy-list) отдельно публикует такой TLS-список и описывает self-signed сертификаты прокси; опубликованный адрес требует собственной протокольной проверки перед выдачей как Alive.

Исключение с собственной проверенной настройкой — [Proxifly](https://github.com/proxifly/free-proxy-list): поставщик определяет `https://IP:PORT` как TLS-соединение до прокси. Встроенные `Proxifly HTTPS` и 35 смешанных `Proxifly country` используют `HttpTlsUnverified`; явно указанные `http://`, `socks4://` и `socks5://` сохраняют свои протоколы. Это политика ProxyHarbor, разрешающая непроверенный сертификат только на участке до прокси, а не утверждение поставщика о доверенности сертификатов. Полная проверка сохранённого HTTPS-feed Proxifly с production VPS 6 октября дала 786 успешных подключений из 954 адресов в этом режиме и ни одного в строгом режиме `HttpTls`; результаты относятся к моменту проверки. Startup обновляет протокол существующих канонических источников, сохраняя Id, Enabled и историю. Пользовательские HTTPS-источники и остальные поставщики сохраняют прежние настройки; импортная очередь старого протокола не используется для нового профиля.

Пользовательские Telegram MTProto-источники поддерживают опубликованные `tg://proxy?server=...&port=...&secret=...`, `tg:proxy?...` и HTTPS-ссылки `/proxy` на `t.me`, `telegram.me`, `telegram.dog`. Адрес берётся из `server`, а не из домена ссылки Telegram; непубличные endpoint и повреждённые secret отклоняются. Поддерживаются 16-байтные secret, варианты `dd` и `ee` в hex или Base64, как в TDLib. JSON допускает массив ссылок/объектов либо обёртку `proxies`; объект содержит `link` или отдельные `server`, `port`, `secret`. Для такого JSON выберите `MtProto` в редакторе VPN-источника. Это Telegram-прокси, а не HTTP/SOCKS-прокси общего назначения.

Канонический MTProto Search URL: `https://freeproxydb.com/api/proxy/search?protocol=mtproto&page_size=100&page_index=1&order_by=id&order_dir=desc`. Он использует сохранение страниц, общую квоту и повторную проверку начала списка наравне с каноническим VPN Search URL. Очерёдность VPN-импорта учитывает возраст сохранённого API capture до приоритета источника, чтобы готовые очереди получали доступ к ограниченному бюджету по очереди.

Операторская таблица всех провайдеров с прямыми ссылками вынесена в [`SOURCE_CATALOG.md`](SOURCE_CATALOG.md); главная страница намеренно не раскрывает источники. Этот документ описывает эксплуатационные гарантии и воспроизводимый аудит.

Они исключены из текущего каталога и списка startup seed. Повторный полный source gate прошёл для всех 547 оставшихся feed без пропусков и усечения, включая обновление существующей базы. Это не подтверждение работоспособности каждого адреса и не проверка доступности новых feed с production VPS. До deployment обязательны остальные применимые CI и публикационные проверки.

Это URL/content-аудит, а не подмена полного сетевого прогона: CI и production release-gate повторяют настоящий collector и validation. Канонические URL, ранги и протоколы находятся в `BuiltInSourceCatalog.cs`. На старте сервис идемпотентно добавляет недостающие встроенные feed'ы даже в существующую БД, обновляет их метаданные и сохраняет ручной выбор администратора `Enabled/Disabled`. Удаляются только явно распознаваемые ранее встроенные URL, включая нестабильное семейство country-feed `XYZS996`; прочие пользовательские источники не затрагиваются. Действующий каталог имеет приоритет над старым списком удаления: восстановленный feed сохраняет идентификатор, настройки, историю и незавершённый снимок импорта при повторном запуске.

Отдельно seed создаёт выключенный управляемый источник **Best Proxies Premium**. Администратор вводит купленный API key в редакторе источника; значение шифруется ASP.NET Core Data Protection, не включается в URL и никогда не возвращается API или браузеру. Замена ключа сбрасывает source backoff и позволяет сразу повторить сбор. Collector различает недействительный (`401`), отказ в доступе (`403`) и ограничение по частоте (`429`), сохраняет только безопасный статус и применяет обычный экспоненциальный backoff. Ответ `403` сам по себе не доказывает истечение ключа: возможны ограничения IP или прав доступа. Срок действия обновляется только через успешный provider key-status endpoint; HTTP-отказ или сбой TTL сохраняет последнюю подтверждённую дату.

Best Proxies подключён отдельным адаптером. Форма создания пользовательского источника принимает публичный HTTPS feed и не создаёт универсальную платную интеграцию. Для другого сервиса нужно отдельно согласовать способ авторизации, формат ответа, пагинацию, ограничения запросов и проверку срока действия. Endpoint управления ключом сейчас доступен только источнику Best Proxies. Секретный ключ другого сервиса нельзя сохранять в обычном URL источника.

Источник должен отдавать сами адреса прокси в поддерживаемом текстовом или JSON-формате. HTML-страницы кабинета, gateway с авторизацией `username/password`, CSV и произвольные структуры JSON требуют соответствующего адаптера. Количество origin identities считается по GitHub owner или DNS hostname; оно не доказывает независимость поставщиков или уникальность адресов.

Для публичного [FreeProxyDB Search API](https://freeproxydb.com/documentation/apiDocs) предусмотрен обработчик полного списка по каноническому URL `https://freeproxydb.com/api/proxy/search?protocol=http,socks4,socks5&page_size=100&page_index=1&order_by=id&order_dir=desc`. Он последовательно читает страницы размером до 100 записей до текущего `total_count` и сохраняет смешанные протоколы и исходные JSON-поля до разбора кандидатов. Общий предел HTTP body остаётся 10 000 000 байт; ошибка или защитный предел не превращаются в успешную загрузку префикса. Без snapshot token пагинация меняющейся базы не доказывает атомарный охват всех удалённых записей.

Публичный список [Proxiware](https://proxiware.com/free-proxy-list) поддерживается по каноническому URL `https://papi.proxiware.com/proxies?page=1&country=&protocol=&anonymity=&speed=`. Сборщик сохраняет страницы по 100 записей до `total_proxies`, продолжает после перезапуска и повторно проверяет начало списка. Идентичность записи определяется полной тройкой `addr`, `port`, `protocol`; изменения скорости или страны не создают новую запись. Объединённые метки `socks4socks5`, `httpsocks4`, `httpsocks5`, `httphttps` и `httpsocks4socks5` разворачиваются в отдельные протоколы только этим адаптером. Существующий массив `protocols` сохраняется. Приватные адреса, неверные порты и credentials по-прежнему отклоняются обычным parser.

Proxiware использует отдельную distributed lease и сохраняемый cooldown: до 20 запросов за цикл с паузой не менее секунды, обновление полного списка не чаще раза в десять минут после последней страницы. Это политика приложения, а не заявленная поставщиком квота. `Retry-After`, лимит 10 МБ, запрет частичного успешного списка и защита HTTP/redirect остаются действующими. Обычный fetch не обходит постраничный адаптер через другой URL этого origin. Поддержка формата и страниц не добавляет источник автоматически и не подтверждает работоспособность всех опубликованных адресов.

Публичный [Socks5Proxies список](https://socks5proxies.com/free-proxy-list/) поддерживается по каноническому URL `https://api.socks5proxies.com/api/proxies?limit=100&offset=0&sort=country`. Проверяются `meta.total`, `meta.limit`, `meta.offset` и массив `data`; endpoint и все явные протоколы сохраняются в компактных страницах вместе с SHA-256 исходного декодированного ответа. Поля credentials заменяются маркерами, которые сохраняют отказ общего parser от таких записей. Данные о стране, задержке и рейтинге поставщика не заменяют собственную проверку адреса. Страницы продолжаются после перезапуска, а сверка начала списка не позволяет публиковать успешный префикс при обнаруженных пропусках, повторе или неверной пагинации. Изменяющийся список без snapshot token не является атомарной выгрузкой.

Socks5Proxies использует отдельную distributed lease, до 20 запросов за цикл и паузу не менее секунды; полный список обновляется не чаще раза в 30 минут после последней страницы. Это политика приложения. Сохраняются предел 10 МБ, предел страницы 2 МБ и общий бюджет хранилища; `Retry-After` и опубликованный `X-RateLimit-Reset` сохраняют более поздний срок следующего запроса. [Документация поставщика](https://socks5proxies.com/docs/api/) описывает публичные endpoints как best-effort и рекомендует API с bearer key для регулярной интеграции. CSV-export с заявленным лимитом 5000 при проверке 7 октября вернул только 100 строк; он не заменяет полный обход. Неканонические API URL и redirects не обходят сохраняемую очередь. Источник не добавляется автоматически, а формат ответа не подтверждает работоспособность всех адресов.

Публичный список [RoundProxies](https://roundproxies.com/free-proxy-list/) поддерживается по каноническому URL `https://roundproxies.com/api/get-free-proxies/?limit=500&page=1&sort_by=lastChecked&sort_type=asc`. Публичный клиент использует `lastChecked`; обратный порядок и размер 500 проверены на реальных ответах API. Сборщик проверяет возвращённые `page`, `limit`, `total` и массив `data`, сохраняет полные идентификаторы `_id` и все опубликованные протоколы. Страницы сохраняются до следующего запроса и продолжаются после перезапуска; повторный обход начала списка учитывает перемещение записей при изменении `lastChecked`. Ошибка, повтор страницы, преждевременный конец или превышение лимита не публикуют успешный префикс. Без snapshot token это не доказывает атомарный охват меняющейся базы.

RoundProxies использует отдельную distributed lease и сохраняемый cooldown: до 20 запросов за цикл с паузой не менее секунды, обновление полного списка не чаще раза в пять минут после последней страницы. Это политика приложения, а не квота поставщика. Сохраняются `Retry-After`, предел 10 МБ, обычная проверка публичных адресов и отказ от credentials. Другие URL этого API, включая HTTP redirects и закодированный путь, не обходят очередь через обычный fetch. HTML-страница самого сайта остаётся доступной обычному обработчику. Поддержка адаптера не добавляет источник автоматически и не подтверждает работоспособность опубликованных прокси.

Успешный полный API-список обновляется не чаще раза в шесть часов — это консервативная политика приложения для публичной light automation, а не опубликованная квота Search API. `429` откладывает следующий запрос до полного `Retry-After` либо на час без заголовка; `503` с будущим `Retry-After` также переносит попытку. Ручной сбор не обходит этот cooldown. Хвост уже сохранённого снимка импортируется в это время обычными порциями. ETag и Last-Modified отдельных страниц не используются для подтверждения собранного полного списка. Квоты Subscribe endpoint не подменяют отдельные per-IP/record ограничения Search.

Проверенные страницы сохраняются в PostgreSQL до следующего запроса, поэтому перезапуск или quota pause продолжают загрузку со следующей страницы. За один цикл допускаются четыре HTTP-запроса; обычный и VPN-сборщики используют общий distributed lease и сохраняемый срок следующего запроса. Локальная пауза между запросами составляет десять секунд, без подмены опубликованных квот. Внутренние transport retry и redirects для API запрещены: новая попытка требует нового разрешённого слота, а изменение канонического endpoint — проверки адаптера. Generic feed не может обратиться к этому origin напрямую или через redirect. После traversal повторно читается начало списка до пересечения с уже полученными ID и покрытия текущего `total_count`; новые ID объединяются, последняя полученная запись заменяет предыдущую. Это не обещание атомарного снимка меняющегося внешнего API.

VPN API поддерживается по отдельному каноническому URL `https://freeproxydb.com/api/proxy/search?protocol=vless,vmess,trojan,ss,hysteria2&page_size=100&page_index=1&order_by=id&order_dir=desc`. Полный `connect_string` передаётся обычным VPN parser и snapshot codec; непубличные endpoint, управляющие символы и некорректные URI не публикуются. Консервативное время наблюдения — самое раннее время сохранённой страницы, поэтому старый API body не заменяет более свежую ссылку другого источника. MTProto этим фильтром не поддерживается. Другие Search URL требуют отдельного адаптера и не обходят общий cooldown через generic fetch.

Остановка на границе цикла и ожидание origin lease не обновляют `LastFetchedAt`, `LastSucceededAt` или `LastContentFetchedAt`; HTTP-ошибка учитывается как неуспешная попытка. Готовый API body остаётся доступным без HTTP, пока целиком не сохранён в candidate snapshot; свежий prefix при занятом старом snapshot не считается полным admission. Сжатые страницы имеют SHA-256, ограничения размера и общий бюджет 64 МиБ. Они и origin deadlines исключены из portable backup; успешный restore очищает их в общей транзакции, а отмена или ошибка сохраняет прежнее состояние.

Платные источники обрабатываются отдельной первой фазой. Поэтому их кандидаты занимают bounded-набор до публичных feed, а при импорте помечаются для немедленной проверки. Validation queue сначала забирает такие строки независимо от прежнего статуса и только потом переходит к обычному порядку. После одной проверки маркер заменяется штатным расписанием, поэтому истёкший ключ не создаёт вечного приоритета.

Для повторного живого аудита после запуска контейнеров:

```powershell
./tools/Audit-SourceFeeds.ps1 -AdminKey 'значение ADMIN_API_KEY' -ReportPath './source-audit.json'
```

Встроенные VPN-feed проверяются отдельно без запуска приложения:

```powershell
./tools/Test-BuiltInVpnSourceEndpoints.ps1
```

Проверка требует ровно 248 уникальных HTTPS URL от 32 провайдеров, непустую лицензию или условия публикации и хотя бы одну поддерживаемую конфигурацию в каждом ответе. В CI используется быстрый `-CatalogOnly`, а еженедельный source-audit выполняет живую сетевую проверку всех VPN-feed.

VPN-аудит 6 октября 2026 года также выявил 27 устаревших URL. Четыре протокольные ленты Black Crow перенесены в `sub/general`; вместо отсутствующего Hysteria2-файла подключён опубликованный владельцем `all_configs.txt` с корректным названием mixed. Пять новых адресов отдельно проверены production parser. Их условия указаны как public subscription links из `SUBSCRIPTIONS.md`, поскольку MIT-лицензия в текущем репозитории не подтверждена. Startup сохраняет Id и Enabled, обновляет метаданные и сбрасывает HTTP-состояние старого resource. 18 недоступных Alexant URL и четыре отсутствующих файла стран Au1rxx удалены из seed. Повторный URL/content-аудит прошёл для всех 248 текущих feed; это не сетевой тест работоспособности каждого VPN endpoint.

Shadowsocks URI поддерживают современный [SIP002](https://shadowsocks.org/doc/sip002.html) и старый формат с полным `method:password@host:port` в Base64, который также распознаёт [официальный Android-клиент](https://github.com/shadowsocks/shadowsocks-android/blob/master/core/src/main/java/com/github/shadowsocks/database/Profile.kt). Старый формат декодируется строгим UTF-8 только для извлечения endpoint; публичная исходная ссылка, query и fragment сохраняются. Декодированный адрес обязан содержать только host и числовой port; проверки публичных IP и канонических DNS-имён сохраняются. Поддержка формата не доказывает успешную авторизацию или VPN handshake.

Скрипт запускает настоящий production-сбор, сохраняет машиночитаемый JSON-отчёт даже при раннем отказе и завершится ошибкой, если admin-команда не вернула завершённый цикл, хотя бы один активный источник не был заново обработан именно в этом цикле, его результат пуст/ошибочен/усечён, forced-run пропустил источник, не создал ни одного уникального кандидата, счётчики `CollectionRun` расходятся с состоянием feed'ов либо достигнут `MaxCandidatesPerRun`. Artifact отдельно сохраняет длительность, число обработанных/пропущенных источников, уникальных кандидатов и новых строк БД. Отдельный completeness-gate требует наличия и включённости всех 547 встроенных feed'ов и ровно 281 технических origin identities. Это не доказательство независимых поставщиков: `providerIdentity` равен GitHub owner либо DNS hostname. Пользовательские feed'ы не искажают эту проверку. Workflow `Source feed audit` повторяет аудит еженедельно и сохраняет отчёт и API-лог как GitHub Actions artifacts.

Содержимое каждого feed'а считается недоверенным: загрузка ограничена 10 000 000 байт, parser работает без backtracking и принимает только публичные IP. `Collector__MaxProxiesPerSource` ограничивает порцию импорта за цикл, а `Collector__MaxCandidatesPerRun` — общий набор admitted кандидатов. Сигнал общей квоты появляется только при отказе новому уникальному endpoint, но не при точном заполнении или повторе уже принятого адреса. Индивидуальные флаги усечения продолжают показывать, что текущий HTTP body больше порции; они не подменяют доказательство полного source-аудита.

Полный распознанный body нормализуется в неизменяемый снимок `ProxySourceImportStates`: максимум 1 000 000 уникальных компактных ключей, страницы по 2048 записей, до 24 000 000 байт сжатого payload на источник и до 512 МиБ суммарно в PostgreSQL. Regex-объекты не накапливаются для всего body, строки endpoint'ов не материализуются в общий промежуточный список. SHA-256 и bounded decompression проверяют cache при чтении. Снимок сохраняется до admission, но cursor подтверждается только после успешного bulk commit; ошибка БД или crash оставляет безопасный повтор. Изменившийся feed не вытесняет ещё не обработанный хвост. Свежий prefix получает до половины той же source-квоты, а оставшаяся порция продолжает старый снимок. При квоте в один адрес свежий prefix и старый хвост чередуются; SHA-256 body предотвращает повтор одного и того же свежего окна. Hash, порядок очередей и время продвижения подтверждаются только после bulk commit, включая порцию без продвижения старого cursor. Отказ общей квоты оставляет неподтверждённое свежее окно для повтора. Внутри платной и публичной фаз первыми идут источники с самым старым подтверждённым продвижением; платные сохраняют приоритет общей квоты. После завершения payload удаляется, остаётся узкая metadata для порядка обработки. Заполнение storage не считается успешным полным импортом: цикл завершается ошибкой после сохранения остальных порций и освобождения их cache.

Pending-снимок может импортироваться во время HTTP backoff или минимального polling interval без сетевого запроса. Такая порция не обновляет `LastFetchedAt`, `LastSucceededAt`, HTTP validators или `NextFetchAt`. Отключение, смена URL/protocol и удаление источника освобождают устаревший cache; portable restore также удаляет снимки через cascade при замене источников. Отсутствие или повреждение import state требует полного body вместо принятия прежнего `304`.

Ответы с `text/html`, `application/xhtml+xml` либо HTML envelope отклоняются даже при HTTP 200 и наличии похожей на `IP:port` строки. Поэтому login, WAF и error page не могут ложно пометить источник успешным и добавить служебный адрес как proxy-кандидат; отсутствующий media type, plain text, JSON и binary feed остаются совместимыми.

JSON-feed может содержать массив строк либо объектов с `ip_address`, `ip`, `host` или `addr` и отдельным `port`; поддерживаются обёртки `results`, `data` и `proxies`, в том числе вложенный `data.data`. Поле `addr` поддерживает публичные ответы Proxiware; при наличии нескольких полей адреса используется первое в указанном порядке, без перехода к другому полю после ошибки. Без отдельного `port` эти поля могут содержать IP и порт вместе. Массив `protocols` разворачивается в HTTP/HTTPS/SOCKS4/SOCKS5-кандидаты; одиночные `protocol` и `type` также учитываются. Лимит и дедупликация общие для всего ответа и всех протоколов. Некорректный JSON, error envelope, неподдерживаемый явный протокол, непубличный IP и записи с непустыми credentials отклоняются; адреса из `message`, diagnostic-полей и ссылок пагинации не извлекаются. Источники с авторизацией самого proxy требуют отдельной защищённой интеграции и не попадают в общий публичный каталог через этот parser.

Когда отдельного `port` нет, поле адреса может содержать `IP:port` или `[IPv6]:port`. Схемы, домены, userinfo и посторонний текст в таком поле не принимаются. При наличии отдельного `port` поле адреса должно содержать только IP: неоднозначная запись с портом в обоих полях отклоняется.

Временные 429/5xx и транспортные сбои повторяются с bounded jitter/backoff. Ответ с непрочитанным body закрывается до ожидания повтора, поэтому недоступный провайдер не удерживает ограниченные connection-pool slots во время паузы.

Для Litport успешный запрос также выставляет `NextFetchAt` на пять минут вперёд: сокращение глобального интервала worker не обходит опубликованную границу polling. Принудительный admin-аудит по-прежнему игнорирует расписание; оператору нельзя запускать его чаще ограничений провайдера.

Успешный `200` сохраняет bounded HTTP validators `ETag` и `Last-Modified` в строке источника, backup и restore. Следующий запрос передаёт их как `If-None-Match`/`If-Modified-Since`; `304 Not Modified` считается свежей успешной проверкой и сохраняет прежние count/truncation. При pending-снимке `304` продолжает старый хвост, если body уже сохранён в исходном снимке или его свежий prefix подтверждён. Для изменившегося body, чей prefix ещё не подтверждён, новые validators не сохраняются: следующий HTTP-запрос должен повторить body, а не потерять свежее окно через `304`. Минимальный polling interval и backoff сохраняются. При завершённом снимке `304` не добавляет кандидатов. Отдельный `LastContentFetchedAt` не меняется на `304`. Когда полный body старше половины membership-retention, но максимум суток, collector выполняет unconditional fetch: это предотвращает необратимую потерю удалённого Pending/Dead proxy из feed с вечным неизменным ETag. Ответ `304` принимается только после прежнего успешного непустого результата, существующего import state и реально отправленного validator. При смене URL/protocol validators и дата полного body сбрасываются, а malformed или содержащий control characters ETag отклоняется fail-closed.

Ручной `POST /api/v1/admin/collect` и вызывающий его source-аудит не отправляют conditional validators: каждый feed обязан вернуть body. JSON и gate требуют `LastContentFetchedAt` каждого enabled source внутри `StartedAt…FinishedAt`, поэтому старый `304` либо сохранённый count не считаются доказательством текущего parser-run.

Для повторной проверки уже сохранённого состояния без нового сетевого сбора можно передать `-SkipCollection`; JSON явно пометит такой отчёт как `collectionTriggered: false`. Плановый workflow этот режим не использует.

Между плановыми аудитами тот же канонический расчёт доступен в `GET /api/v1/admin/diagnostics`, закрытой React admin-панели и Prometheus. `proxyharbor_source_catalog_complete` отвечает за присутствие и включённость 547/281, а `proxyharbor_source_catalog_healthy` становится равен `1` лишь после свежего успешного непустого результата каждого встроенного feed'а. Свежесть ограничена тремя настроенными интервалами сбора и отдельно видна в `proxyharbor_builtin_sources_stale`. Для VPN действует отдельный независимый набор `proxyharbor_vpn_source_catalog_complete`, `proxyharbor_vpn_source_catalog_healthy` и `proxyharbor_builtin_vpn_sources_*`: пользовательские VPN-feed не могут скрыть отсутствие или отказ одного из 248 встроенных URL и 32 провайдеров.
