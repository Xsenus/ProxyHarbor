# Каталог источников ProxyHarbor

Операторская таблица всех провайдеров с прямыми ссылками вынесена в [`SOURCE_CATALOG.md`](SOURCE_CATALOG.md); главная страница намеренно не раскрывает источники. Этот документ описывает эксплуатационные гарантии и воспроизводимый аудит.

Встроенный каталог содержит **547 proxy-feed и 281 техническую origin identity** с потоками HTTP/HTTPS/SOCKS4/SOCKS5. VPN-каталог содержит **248 HTTPS feed от 32 провайдеров** для OpenVPN, WireGuard, VLESS, VMess, Trojan, Shadowsocks, Hysteria2 и TUIC.

Аудит 6 октября 2026 года через production collector на отдельной локальной БД обнаружил восемь неисправных встроенных URL: три пустых экспорта ProxyMan, недоступные репозитории iamthebestm85, just-not-google, Allaux, ProTechEx и удалённый country-файл HProxy DZ. Они исключены из текущего каталога и списка startup seed. Повторный полный source gate прошёл для всех 547 оставшихся feed без пропусков и усечения, включая обновление существующей базы. Это не подтверждение работоспособности каждого адреса и не проверка доступности новых feed с production VPS. До deployment обязательны остальные применимые CI и публикационные проверки.

Аудит **14 сентября 2026 года** сопоставил канонический каталог с фактическими production-результатами и отдельно проверил новые URL с VPS. Пустой GProxyNet, HTML-страница CyberGateway, локальные loopback-порты KhaiNguyenDuc и ошибочно классифицированная MetaFetch subscription удалены из proxy-каталога. Пять feed размером 18–23 МБ также заменены: один из них содержал 1 193 021 уникальный endpoint и неизбежно нарушал ограничение `MaxProxiesPerSource`. Защитный лимит 10 МБ сохранён без исключений. MetaFetch добавлен в VPN-каталог, а три отсутствующих country-feed Au1rxx (AF, MU и BE) удалены. Все остальные VPN URL повторно проверены на доступность и разбираемое содержимое. Это URL/content-аудит, а не подмена полного сетевого прогона: CI и production release-gate повторяют настоящий collector и validation. Каноническая дата `LastAuditedOn` публикуется в admin diagnostics и Prometheus.

Канонические URL, ранги и протоколы находятся в `BuiltInSourceCatalog.cs`. На старте сервис идемпотентно добавляет недостающие встроенные feed'ы даже в существующую БД, обновляет их метаданные и сохраняет ручной выбор администратора `Enabled/Disabled`. Удаляются только явно распознаваемые ранее встроенные URL, включая нестабильное семейство country-feed `XYZS996`; прочие пользовательские источники не затрагиваются.

Отдельно seed создаёт выключенный управляемый источник **Best Proxies Premium**. Администратор вводит купленный API key в редакторе источника; значение шифруется ASP.NET Core Data Protection, не включается в URL и никогда не возвращается API или браузеру. Замена ключа сбрасывает source backoff и позволяет сразу повторить сбор. Collector различает недействительный (`401`), отказ в доступе (`403`) и ограничение по частоте (`429`), сохраняет только безопасный статус и применяет обычный экспоненциальный backoff. Ответ `403` сам по себе не доказывает истечение ключа: возможны ограничения IP или прав доступа. Срок действия обновляется только через успешный provider key-status endpoint; HTTP-отказ или сбой TTL сохраняет последнюю подтверждённую дату.

Best Proxies подключён отдельным адаптером. Форма создания пользовательского источника принимает публичный HTTPS feed и не создаёт универсальную платную интеграцию. Для другого сервиса нужно отдельно согласовать способ авторизации, формат ответа, пагинацию, ограничения запросов и проверку срока действия. Endpoint управления ключом сейчас доступен только источнику Best Proxies. Секретный ключ другого сервиса нельзя сохранять в обычном URL источника.

Источник должен отдавать сами адреса прокси в поддерживаемом текстовом или JSON-формате. HTML-страницы кабинета, gateway с авторизацией `username/password`, CSV и произвольные структуры JSON требуют соответствующего адаптера. Количество origin identities считается по GitHub owner или DNS hostname; оно не доказывает независимость поставщиков или уникальность адресов.

Для публичного [FreeProxyDB Search API](https://freeproxydb.com/documentation/apiDocs) предусмотрен обработчик полного списка по каноническому URL `https://freeproxydb.com/api/proxy/search?protocol=http,socks4,socks5&page_size=100&page_index=1&order_by=id&order_dir=desc`. Он последовательно читает страницы размером до 100 записей до текущего `total_count` и сохраняет смешанные протоколы и исходные JSON-поля до разбора кандидатов. Общий предел HTTP body остаётся 10 000 000 байт; ошибка или защитный предел не превращаются в успешную загрузку префикса. Без snapshot token пагинация меняющейся базы не доказывает атомарный охват всех удалённых записей.

Успешный полный API-список обновляется не чаще раза в шесть часов — это консервативная политика приложения для публичной light automation, а не опубликованная квота Search API. `429` откладывает следующий запрос до полного `Retry-After` либо на час без заголовка; `503` с будущим `Retry-After` также переносит попытку. Ручной сбор не обходит этот cooldown. Хвост уже сохранённого снимка импортируется в это время обычными порциями. ETag и Last-Modified отдельных страниц не используются для подтверждения собранного полного списка. Квоты Subscribe endpoint не подменяют отдельные per-IP/record ограничения Search.

Платные источники обрабатываются отдельной первой фазой. Поэтому их кандидаты занимают bounded-набор до публичных feed, а при импорте помечаются для немедленной проверки. Validation queue сначала забирает такие строки независимо от прежнего статуса и только потом переходит к обычному порядку. После одной проверки маркер заменяется штатным расписанием, поэтому истёкший ключ не создаёт вечного приоритета.

Для повторного живого аудита после запуска контейнеров:

```powershell
./tools/Audit-SourceFeeds.ps1 -AdminKey 'значение ADMIN_API_KEY' -ReportPath './source-audit.json'
```

Встроенные VPN-feed проверяются отдельно без запуска приложения:

```powershell
./tools/Test-BuiltInVpnSourceEndpoints.ps1
```

Проверка требует ровно 248 уникальных HTTPS URL от 32 провайдеров, непустую лицензию или условия публикации и хотя бы одну поддерживаемую конфигурацию в каждом ответе. В CI используется быстрый `-CatalogOnly`, а еженедельный source-audit выполняет живую сетевую проверку всех VPN-feed.

VPN-аудит 6 октября 2026 года также выявил 27 устаревших URL. Четыре протокольные ленты Black Crow перенесены в `sub/general`; вместо отсутствующего Hysteria2-файла подключён опубликованный владельцем `all_configs.txt` с корректным названием mixed. Пять новых адресов отдельно проверены production parser. Их условия указаны как public subscription links из `SUBSCRIPTIONS.md`, поскольку MIT-лицензия в текущем репозитории не подтверждена. Startup сохраняет Id и Enabled, обновляет метаданные и сбрасывает HTTP-состояние старого resource. 18 недоступных Alexant URL и четыре отсутствующих файла стран Au1rxx удалены из seed. Повторный URL/content-аудит прошёл для всех 248 текущих feed; это не сетевой тест работоспособности каждого VPN endpoint.

Shadowsocks URI поддерживают современный [SIP002](https://shadowsocks.org/doc/sip002.html) и старый формат с полным `method:password@host:port` в Base64, который также распознаёт [официальный Android-клиент](https://github.com/shadowsocks/shadowsocks-android/blob/master/core/src/main/java/com/github/shadowsocks/database/Profile.kt). Старый формат декодируется строгим UTF-8 только для извлечения endpoint; публичная исходная ссылка, query и fragment сохраняются. Декодированный адрес обязан содержать только host и числовой port; проверки публичных IP и канонических DNS-имён сохраняются. Поддержка формата не доказывает успешную авторизацию или VPN handshake.

Скрипт запускает настоящий production-сбор, сохраняет машиночитаемый JSON-отчёт даже при раннем отказе и завершится ошибкой, если admin-команда не вернула завершённый цикл, хотя бы один активный источник не был заново обработан именно в этом цикле, его результат пуст/ошибочен/усечён, forced-run пропустил источник, не создал ни одного уникального кандидата, счётчики `CollectionRun` расходятся с состоянием feed'ов либо достигнут `MaxCandidatesPerRun`. Artifact отдельно сохраняет длительность, число обработанных/пропущенных источников, уникальных кандидатов и новых строк БД. Отдельный completeness-gate требует наличия и включённости всех 547 встроенных feed'ов и ровно 281 технических origin identities. Это не доказательство независимых поставщиков: `providerIdentity` равен GitHub owner либо DNS hostname. Пользовательские feed'ы не искажают эту проверку. Workflow `Source feed audit` повторяет аудит еженедельно и сохраняет отчёт и API-лог как GitHub Actions artifacts.

Содержимое каждого feed'а считается недоверенным: загрузка ограничена 10 000 000 байт, parser работает без backtracking и принимает только публичные IP. `Collector__MaxProxiesPerSource` ограничивает порцию импорта за цикл, а `Collector__MaxCandidatesPerRun` — общий набор admitted кандидатов. Сигнал общей квоты появляется только при отказе новому уникальному endpoint, но не при точном заполнении или повторе уже принятого адреса. Индивидуальные флаги усечения продолжают показывать, что текущий HTTP body больше порции; они не подменяют доказательство полного source-аудита.

Полный распознанный body нормализуется в неизменяемый снимок `ProxySourceImportStates`: максимум 1 000 000 уникальных компактных ключей, страницы по 2048 записей, до 24 000 000 байт сжатого payload на источник и до 512 МиБ суммарно в PostgreSQL. Regex-объекты не накапливаются для всего body, строки endpoint'ов не материализуются в общий промежуточный список. SHA-256 и bounded decompression проверяют cache при чтении. Снимок сохраняется до admission, но cursor подтверждается только после успешного bulk commit; ошибка БД или crash оставляет безопасный повтор. Изменившийся feed не вытесняет ещё не обработанный хвост. Свежий prefix получает до половины той же source-квоты, а оставшаяся порция продолжает старый снимок. При квоте в один адрес свежий prefix и старый хвост чередуются; SHA-256 body предотвращает повтор одного и того же свежего окна. Hash, порядок очередей и время продвижения подтверждаются только после bulk commit, включая порцию без продвижения старого cursor. Отказ общей квоты оставляет неподтверждённое свежее окно для повтора. Внутри платной и публичной фаз первыми идут источники с самым старым подтверждённым продвижением; платные сохраняют приоритет общей квоты. После завершения payload удаляется, остаётся узкая metadata для порядка обработки. Заполнение storage не считается успешным полным импортом: цикл завершается ошибкой после сохранения остальных порций и освобождения их cache.

Pending-снимок может импортироваться во время HTTP backoff или минимального polling interval без сетевого запроса. Такая порция не обновляет `LastFetchedAt`, `LastSucceededAt`, HTTP validators или `NextFetchAt`. Отключение, смена URL/protocol и удаление источника освобождают устаревший cache; portable restore также удаляет снимки через cascade при замене источников. Отсутствие или повреждение import state требует полного body вместо принятия прежнего `304`.

Ответы с `text/html`, `application/xhtml+xml` либо HTML envelope отклоняются даже при HTTP 200 и наличии похожей на `IP:port` строки. Поэтому login, WAF и error page не могут ложно пометить источник успешным и добавить служебный адрес как proxy-кандидат; отсутствующий media type, plain text, JSON и binary feed остаются совместимыми.

JSON-feed может содержать массив строк либо объектов с `ip_address`, `ip` или `host` и отдельным `port`; поддерживаются обёртки `results`, `data` и `proxies`, в том числе вложенный `data.data`. Массив `protocols` разворачивается в HTTP/HTTPS/SOCKS4/SOCKS5-кандидаты; одиночные `protocol` и `type` также учитываются. Лимит и дедупликация общие для всего ответа и всех протоколов. Некорректный JSON, error envelope, неподдерживаемый явный протокол, непубличный IP и записи с непустыми credentials отклоняются; адреса из `message`, diagnostic-полей и ссылок пагинации не извлекаются. Источники с авторизацией самого proxy требуют отдельной защищённой интеграции и не попадают в общий публичный каталог через этот parser.

Временные 429/5xx и транспортные сбои повторяются с bounded jitter/backoff. Ответ с непрочитанным body закрывается до ожидания повтора, поэтому недоступный провайдер не удерживает ограниченные connection-pool slots во время паузы.

Для Litport успешный запрос также выставляет `NextFetchAt` на пять минут вперёд: сокращение глобального интервала worker не обходит опубликованную границу polling. Принудительный admin-аудит по-прежнему игнорирует расписание; оператору нельзя запускать его чаще ограничений провайдера.

Успешный `200` сохраняет bounded HTTP validators `ETag` и `Last-Modified` в строке источника, backup и restore. Следующий запрос передаёт их как `If-None-Match`/`If-Modified-Since`; `304 Not Modified` считается свежей успешной проверкой и сохраняет прежние count/truncation. При pending-снимке `304` продолжает старый хвост, если body уже сохранён в исходном снимке или его свежий prefix подтверждён. Для изменившегося body, чей prefix ещё не подтверждён, новые validators не сохраняются: следующий HTTP-запрос должен повторить body, а не потерять свежее окно через `304`. Минимальный polling interval и backoff сохраняются. При завершённом снимке `304` не добавляет кандидатов. Отдельный `LastContentFetchedAt` не меняется на `304`. Когда полный body старше половины membership-retention, но максимум суток, collector выполняет unconditional fetch: это предотвращает необратимую потерю удалённого Pending/Dead proxy из feed с вечным неизменным ETag. Ответ `304` принимается только после прежнего успешного непустого результата, существующего import state и реально отправленного validator. При смене URL/protocol validators и дата полного body сбрасываются, а malformed или содержащий control characters ETag отклоняется fail-closed.

Ручной `POST /api/v1/admin/collect` и вызывающий его source-аудит не отправляют conditional validators: каждый feed обязан вернуть body. JSON и gate требуют `LastContentFetchedAt` каждого enabled source внутри `StartedAt…FinishedAt`, поэтому старый `304` либо сохранённый count не считаются доказательством текущего parser-run.

Для повторной проверки уже сохранённого состояния без нового сетевого сбора можно передать `-SkipCollection`; JSON явно пометит такой отчёт как `collectionTriggered: false`. Плановый workflow этот режим не использует.

Между плановыми аудитами тот же канонический расчёт доступен в `GET /api/v1/admin/diagnostics`, закрытой React admin-панели и Prometheus. `proxyharbor_source_catalog_complete` отвечает за присутствие и включённость 547/281, а `proxyharbor_source_catalog_healthy` становится равен `1` лишь после свежего успешного непустого результата каждого встроенного feed'а. Свежесть ограничена тремя настроенными интервалами сбора и отдельно видна в `proxyharbor_builtin_sources_stale`. Для VPN действует отдельный независимый набор `proxyharbor_vpn_source_catalog_complete`, `proxyharbor_vpn_source_catalog_healthy` и `proxyharbor_builtin_vpn_sources_*`: пользовательские VPN-feed не могут скрыть отсутствие или отказ одного из 248 встроенных URL и 32 провайдеров.
